# چرا تراکنش چندسندی نداریم؟ (DB-03 — 🌊 W5)

> وضعیت: طراحی عمدی و مستند، نه بدهی فنی پنهان.

## ۱) یافته‌ی ممیزی

جست‌وجوی کامل کد (`db/*.py`، روترها، جاب‌ها):

- **صفر** استفاده از `session` / `start_session` / `with_transaction`؛
- همه‌ی writeها `update_one` / `insert_one` / `delete_*` ی **تک‌سندی** هستند؛
- هیچ writeای «اتمی‌بودن چند کالکشن» را فرض نکرده است.

## ۲) چرا این قابل‌قبول است؟

| الگو | کجا | چرا کافی است |
|---|---|---|
| upsert تک‌سندیِ per-key روی `bot_settings/_id=global` | `db/core.py::set_setting` | اتمی‌بودن سطح سند مونگو؛ کش با lock بی‌اعتبار می‌شود |
| claim اتمیک (insert-if-absent / findAndModify) | `op_claim`، صف‌ها، DLQ | دقیقاً-یک‌بار بودن بدون تراکنش |
| جاب‌های idempotent + شمارنده‌ی `consec_fail` | بکاپ خودکار، retention، outbox | کرش وسط کار = اجرای مجدد بی‌خطر |
| restore از نوع merge/upsert | `backup.py` | تکرار بازیابی، داده را خراب نمی‌کند |

مونگو اتمی‌بودن **تک‌سند** را تضمین می‌کند و مدل داده‌ی ما طوری طراحی شده
که هیچ invariantای «دو سند یا هیچ‌کدام» لازم نداشته باشد.

## ۳) قراردادهای کرش (تست‌شده در `tests/test_w5_reliability_audit.py`)

1. **upsert هم‌زمان**: N نویسنده‌ی موازی روی کلیدهای مختلف یک سند ⇒
   همه‌ی کلیدها با مقدار کامل و ناگسسته ذخیره می‌شوند (last-writer-wins
   در سطح کلید، نه سندِ پاره).
2. **کرش وسط پایپ‌لاین چندمرحله‌ای**: اجرای مجدد با همان کلید idempotency ⇒
   مرحله‌های انجام‌شده رد می‌شوند؛ **بدون** اثر دوبل (no double-grant).
3. **claim رقابتی**: دو claim هم‌زمان ⇒ دقیقاً یکی `True`.

## ۴) قانون آینده (خط قرمز)

اگر روزی writeای لازم شد که «دو کالکشن یا هیچ‌کدام» باشد:

1. اول ثابت کن با claim/idempotency حل نمی‌شود؛
2. بعد تراکنش + **تست کرش واقعی** (kill وسط commit) + به‌روزرسانی همین سند.

تا آن روز: **تراکنش ممنوع** — پیچیدگی بدون نیاز.
